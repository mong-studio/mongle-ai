> 우리가 만들려는 구조: **(1) 꼬리질문으로 빠진 정보 채우기 → (2) 계획 만들기 →

## 1. LLM-Modulo — "AI는 아이디어만, 채점은 따로 한다"
*Kambhampati et al. (2024), LLMs Can't Plan, But Can Help Planning in LLM-Modulo Frameworks (ICML)*
🔗 https://arxiv.org/pdf/2402.01817

**비유 🍳**
요리사(AI)는 요리를 빠르게 만들지만, 가끔 소금을 두 번 넣어요.
그래서 옆에 **맛 검사하는 선생님(검증자)** 을 둡니다.
요리사가 만들면 → 선생님이 먹어보고 "너무 짜! 다시!" 하고 알려주고 →
요리사가 고쳐 만들고 → 다시 검사… 이걸 통과할 때까지 반복합니다.

**핵심**
- AI는 **계획을 혼자 완벽하게 못 짭니다.** (특히 숫자·날짜 계산)
- 그래서 AI는 "후보 계획"만 내고, **외부 검사기**가 규칙 위반을 잡아냅니다.
- 잘못된 부분은 다시 AI에게 알려줘서(backprompt) 고치게 합니다. → 통과할 때까지 반복.

**우리한테 쓰는 법**
- AI(plan_generator)는 일정 "아이디어 + 난이도"만.
- 코드가 캘린더에 배치, **judge가 "이 조합 말 되나?" 검사**.
- 이게 "하루에 빡센 일 2개" 같은 문제를 잡는 바로 그 구조입니다.

**🔧 방법론 (자세히)**
- 루프 이름 = **Generate-Test-Critique** ("LLM-Modulo"는 SAT Modulo Theories에서 따온 이름).
- 흐름: LLM이 후보 계획을 "추측" → **Reformulator**가 검증용 형식(타임라인/PDDL/JSON)으로 변환 → **비평가 뱅크(bank of critics)** 검사 → **Meta(Backprompt) Controller**가 비평을 모아 다음 프롬프트로 되먹임 → **모든 hard critic 통과 시 종료**(사례는 round 상한 10~15회로도 종료).
- 비평가 3종: **hard**(정확성·외부 검증기 VAL 같은 것, LLM은 못 맡음) / **soft=style**(취향·설명가능성, LLM·VLM이 대행 가능) / **constructive**(틀렸다 판정 넘어 대안까지 제안).
- 정식 보장: **건전성은 hard critic에서 상속**. LLM은 **자기검증을 안 함**(self-critique로 self-improve 불가 — 외부 비평이 필터링해야 함).
- 수치: 자율(LLM 단독) baseline은 **~12%만** 성공 / VAL 되먹임으로 Blocksworld **82%**·Logistics 70% / TravelPlanner는 baseline 0.7%의 **6배**(※ 이건 본편의 GPT-3.5 수치, 2번 case study의 4.6배와 다름).

## 2. LLM-Modulo 여행 계획 사례 — "진짜로 잘 되더라"
*Robust Planning with LLM-Modulo Framework: Case Study in Travel Planning (2024)*
🔗 https://arxiv.org/pdf/2405.20625

**비유 ✈️**
"3박 4일 여행 짜줘"는 우리 "한 달 일정 짜줘"랑 똑같이 어려운 문제예요.
가야 할 곳, 시간, 돈… 지켜야 할 규칙이 많거든요.

**핵심**
- 1번(LLM-Modulo) 방법을 **실제 여행 일정 짜기**에 써봤더니,
- 그냥 AI한테 시킨 것보다 **4.6배 잘**(GPT-4-Turbo: 4.4% → 20.6%) 만들었습니다.
  *(논문 abstract가 "4.6x"로 명시. 흔히 도는 "6배"는 본편 논문의 GPT-3.5 TravelPlanner 수치라 혼동 주의.)*
- "꼭 지킬 규칙(hard)"과 "있으면 좋은 취향(soft)"을 둘 다 다룹니다.

**🔧 방법론 (자세히)**
- TravelPlanner **validation 180쿼리·sole-planning**(DB를 프롬프트에 다 주고 도구사용 없음).
- critic 3그룹(전부 binary): **Format(JSON 유효성 — 다른 검사의 전제)** → **Hard**(Budget·RoomType·Cuisine·Transport) → **Commonsense=style critic**(정보완전성·다양성·일정유효성).
- metacontroller는 단순 — 모든 backprompt를 **이어붙여(concatenate)** 초기 프롬프트 뒤에 붙여 재전달. **최대 10 iteration** 또는 전원 통과 시 종료.
- plan 표현 = **하루당 JSON 1객체**(reformulator가 자연어 plan → JSON 변환 후 검증).
- ablation(GPT-3.5 Final Pass Rate): Common 2.8% / Hard 1.6% / Json 1.1% / **All 5.0%** — 합치면(composability) 올라감. GPT-3.5 LLM-Modulo(5%)가 GPT-4 baseline(4.4%)을 추월.

**우리한테 쓰는 법**
- 여행 일정 ≈ 우리 일상 일정. 거의 같은 문제라 **바로 따라 할 수 있는 본보기**.
- 우리도 hard(마감, 겹치면 안 됨) / soft(아침형 선호 등)로 나눠서 검사하면 됨.

## 3. Clarify When Necessary — "언제, 무엇을 물어볼까"
*Zhang & Choi (2023), Clarify When Necessary: Resolving Ambiguity Through Interaction with LMs*
🔗 https://arxiv.org/pdf/2311.09469

**비유 🙋**
선생님이 숙제를 내줬는데 "동물 그려와"라고만 했어요.
똑똑한 학생은 **"강아지요, 고양이요?"** 하고 먼저 물어봅니다.
근데 너무 다 물어보면 귀찮으니까, **헷갈릴 때만** 물어봐야 해요.

**핵심**
질문하기를 3단계로 딱 나눴습니다.
1. **언제 물을까** (헷갈릴 때만, 확실하면 그냥 진행)
2. **무엇을 물을까** (가장 도움 되는 질문 하나)
3. **답을 받고 결과 만들기**

**우리한테 쓰는 법**
- 우리 follow_up(꼬리질문) 노드의 설계도 그 자체.
- "꼬리질문 언제 멈출까?" → 1번이 답: **헷갈림이 사라지면 멈춤** (필수 칸 다 차면 끝).

**🔧 방법론 (자세히)**
- "언제 묻나"를 **분류 문제가 아니라 불확실성 추정**으로 정식화. 핵심 구분:
  **aleatoric(모호성) 높고 epistemic(지식 부족) 낮은** 입력만 골라 물음 — *물으면 답을 알 수 있는* 경우.
- **INTENT-SIM 알고리즘**: 질문 q 생성 → `[x;q]`에 사용자 답변 **10개 샘플(T=0.5)** →
  DeBERTa-NLI로 동치 답변 묶어 **의도 분포** 구성 → 그 분포의 **엔트로피**가 불확실성 점수.
  (기존 semantic entropy는 *출력* 공간을 보지만, 이건 *사용자 의도* 공간을 봄.)
- 운용: 고정 임계값 대신 **상호작용 예산 b%** — 불확실성 상위 b% 입력에만 질문(selective prediction).
- 결과: **10%에만 질문해도 랜덤 선택 대비 이득 2배**. 지표 = 고정예산 성능 + AUROC.
- ※ 질문 *생성*법은 새로 제안 안 함(평가용 oracle만 둠). 데이터: AmbigQA·AmbiEnt·DiscourseMT.

## 4. What Prompts Don't Say — "사람은 항상 말 안 한 게 있다"
*What Prompts Don't Say: Understanding and Managing Underspecification in LLM Prompts (2025)*
🔗 https://arxiv.org/html/2505.13360v2

**비유 🗣️**
"라면 끓여줘"라고 했을 때, 사실 속마음엔
"덜 맵게, 계란 넣고, 면은 꼬들하게"가 있어요. 근데 입으로 다 말 안 해요.
AI는 이 **숨은 조건**을 모르고 그냥 끓여버립니다.

**핵심**
- 사람의 요청에는 **항상 빠진 조건**이 있습니다(underspecification).
- AI는 모자란데도 자신 있게 답해버려서 엉뚱한 결과가 나옵니다.
- 그래서 **빠진 걸 찾아 되묻는 장치**가 필요합니다.

**우리한테 쓰는 법**
- "왜 꼬리질문이 필요한가"의 근거.
- 일상 목표("운동 좀 할래")는 빠진 조건투성이 → 되묻기 없으면 엉뚱한 일정이 나옴.

**🔧 방법론 (자세히)**
- underspecification 정의 = "**유효하지만 서로 모순되는 동작이 여럿** 가능한" 상태.
- 측정: 태스크당 요구사항 20개를 큐레이션 → 같은 요구사항이 **명시 vs 미명시**일 때 만족률 차이(총 8,400 데이터포인트).
- 수치: 미명시여도 **41%는 LLM이 알아서 맞춤**(추측) / 미명시 시 평균 **−22.6%**, 최악 **−93.1%** / 미명시는 변동성·모델 업데이트 회귀가 각각 약 **2배**.
- **다 명시한다고 정답 아님**: 19개를 한꺼번에 명시하면 오히려 **−19%**(specification overload).
- 완화책 2종: **COPRO-R**(요구사항별 검증기 정확도를 최적화 신호로 → +5.8%) / **Bayesian TPE**(어떤 요구사항을 명시할지 조합 탐색 → +3.8% & 토큰 −41~45%).
- → 우리 식으로: 슬롯을 *다 묻지 말고* 빠지면 치명적인 것만(plan_kind별 필수 슬롯) 묻는 게 옳다는 정량 근거.

## 5. Curiosity by Design — "모자란 요청은 먼저 되물어라"
*Curiosity by Design: An LLM-based Coding Assistant Asking Clarification Questions (2025)*
🔗 https://arxiv.org/pdf/2507.21285

**비유 🤖**
심부름을 시키면 무작정 뛰어가는 동생 말고,
**"형, 그거 빨간 거? 파란 거?" 하고 한 번 묻고 가는 동생**이 실수를 덜 합니다.

**핵심**
- 요청이 **충분한지 먼저 판단하는 분류기**를 둡니다(intent clarity classifier).
- 모자라면 **답하기 전에 먼저 명확화 질문**을 던집니다.
- 그래서 결과물의 정확도가 올라갑니다.

**우리한테 쓰는 법**
- 3번이 "언제·무엇을 물을지 이론"이면, 이건 **"실제로 이렇게 만들면 된다"는 구현 예시**.
- "충분한지 판단 → 모자라면 질문 → 그다음 출력" 순서를 그대로 차용.

**🔧 방법론 (자세히)**
- **3단계 파이프라인**: ① Intent Clarity Classifier(**DistilBERT**, 4점 명확도 척도, 정확도 **73%**, GPT-4o-mini 합성 4,161건으로 학습) → ② Clarification 모듈(**Gemma-3-1B-IT + LoRA**) → ③ Answering.
- 의사결정: 분류 후 사실상 **1회 질문만**(멀티턴 루프 없음), 질문 뒤 재분류로 충분성 판단.
- ⚠️ **그대로 베끼면 안 되는 점**(우리 서비스 관점):
  - 평가가 객관 pass-rate가 아니라 **인간 선호 Likert**(최대치 "더 정확하다 66%").
  - 추론 **평균 133초/건** — 실시간 서비스 부적합.
  - GitHub 실데이터는 노이즈로 폐기 → **전부 합성 데이터**라 실제 쿼리 다양성 미반영.
- → 구조(분류→1회질문→답변)는 우리 planner_node와 1:1로 맞지만, **임계값·다회 루프·비용**은 우리가 따로 설계해야 함.

## 우리 파이프라인과 연결 (요약)

```
사용자: "이번 달에 운동이랑 공부 좀 챙기고 싶어"   ← 빠진 조건 많음 (논문 4)
        │
   [follow_up] 헷갈리는 것만 되묻기                ← 논문 3, 5
        │   "운동은 주 몇 회? 공부는 무슨 시험?"
        ▼
   [plan_generator] 일정 아이디어 + 난이도 매기기   ← 논문 1
        │
   [코드] 캘린더에 규칙 지켜 배치 (날짜 계산)        ← 논문 1, 2
        │
   [judge] "이 조합 말 되나?" 검사 → 이상하면 되돌림  ← 논문 1, 2
        ▼
   완성된 한 달 일정표
```

- **꼬리질문이 필요한 이유** → 논문 4
- **꼬리질문을 어떻게/언제** → 논문 3, 5
- **분배는 코드로, 검증은 따로** → 논문 1, 2
