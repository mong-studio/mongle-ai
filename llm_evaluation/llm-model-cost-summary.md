# 후보 LLM 모델 비용 및 평가 결과 정리

## 1. 요약

본 문서는 몽글마을 LLM 후보 모델의 실행 비용 관점과 현재까지의 평가 결과를 정리한다.

후보 모델 대부분은 Hugging Face에서 제공되는 오픈소스 또는 오픈웨이트 기반 모델이므로, 직접 다운로드해 실행하는 경우 모델 제공사에 호출별 토큰 비용을 지불하지 않는다. 다만 RunPod 같은 GPU 서버 실행 비용, 모델 로드 가능성, 라이선스 조건, 추론 속도, 생성 품질을 함께 고려해야 한다.

현재 평가 결과 기준으로 단일 모델을 하나만 선택한다면 `qwen-7b`가 가장 유력한 후보이다. `midm-base`는 최종 품질 점수와 감성 품질이 가장 높지만 평균 응답 시간이 길고, `kanana-nano-2.1b`는 빠르지만 구조 안정성과 다양성 지표가 낮다. `qwen-7b`는 응답 속도 측면에서는 부담이 있지만, 최종 품질, 한국어 출력 안정성, 의미 유사도, 다양성 지표를 함께 봤을 때 가장 균형적인 단일 후보이다.

## 3. 평가 기준

점수는 5점 만점 기준으로 정리했다. 추가 의미 유사도와 다양성 지표는 0~1 범위에 가까우며, 모델 간 상대 비교에 사용했다.

| 지표 | 설명 |
| --- | --- |
| `auto_score` | Python 규칙 기반 자동 정량 평가 점수 |
| `judge_score` | GPT-5.5 심판 모델 정성 평가 점수 |
| `final_score` | `auto_score * 0.45 + judge_score * 0.55` |
| `json_parse_success_rate` | JSON 파싱 성공률 |
| `schema_success_rate` | 필수 스키마 준수율 |
| `korean_output_rate` | 한국어 출력률 |
| `length_success_rate` | 글자 수 제한 준수율 |
| `avg_latency_sec` | 샘플당 평균 응답 시간 |
| `speed_score` | 응답 속도 5점 환산 점수 |
| `embedding_cosine_similarity` | 생성 출력과 기준 출력의 임베딩 cosine similarity |
| `bertscore_f1` | 생성 출력과 기준 출력의 contextual token similarity |
| `pairwise_cosine_similarity` | 같은 샘플에 대한 모델 간 출력 유사도 |
| `distinct_1`, `distinct_2` | 생성 텍스트의 unigram/bigram 다양성 |

평가 기능은 다음 5개이다.

1. TODO 자동 생성
2. 플래너 챗봇
3. 캐릭터 퀘스트 생성
4. 캐릭터 피드 글 생성
5. 캐릭터 말투/답글 메시지 생성

## 4. 테스트 과정

### 4.1 테스트 목적

테스트의 목적은 단순히 가장 높은 품질의 모델을 찾는 것이 아니라, 몽글마을 서비스에 실제로 적용 가능한 모델을 고르는 것이었다. 따라서 다음 조건을 함께 확인했다.

| 확인 항목 | 설명 |
| --- | --- |
| 기능 적합성 | TODO, 플래너, 퀘스트, 피드, 캐릭터 메시지 기능을 수행할 수 있는지 확인 |
| 구조 안정성 | JSON 파싱과 필수 스키마를 안정적으로 지키는지 확인 |
| 한국어 출력 | 사용자에게 보여줄 수 있는 자연스러운 한국어 응답인지 확인 |
| 감성 품질 | 캐릭터 메시지와 피드 글이 몽글마을의 따뜻한 톤에 맞는지 확인 |
| 응답 속도 | 실제 서비스에서 사용자가 기다릴 수 있는 수준인지 확인 |
| 운영 가능성 | 모델 로드, 라이선스, gated access, 환경 호환성 문제를 함께 확인 |
| 의미 유사도와 다양성 | 기준 출력과의 의미 유사도, 모델별 표현 다양성을 추가로 확인 |

### 4.2 테스트 데이터 구성

| 평가 기능 | 데이터 파일 | 샘플 수 | 평가 내용 |
| --- | --- | --- | --- |
| TODO 자동 생성 | `todo_decomposition_samples.json` | 10 | 사용자의 자연어 할 일 문장을 TODO 목록으로 분해 |
| 플래너 챗봇 | `planner_samples.json` | 10 | 일정 계획 또는 추가 질문 응답 생성 |
| 퀘스트 생성 | `quest_samples.json` | 10 | 사용자 TODO를 캐릭터 세계관의 퀘스트로 변환 |
| 피드 글 생성 | `feed_samples.json` | 10 | 완료된 퀘스트를 캐릭터 피드 글로 변환 |
| 캐릭터 메시지/답글 | `character_message_samples.json` | 10 | TODO 완료 메시지와 댓글 답글 생성 |

각 모델은 총 50개 샘플을 평가했다. 샘플은 실제 사용자 데이터가 아니라 문서 규칙에 맞춰 준비된 합성 데이터이며, 캐릭터 메시지/답글 샘플에는 댓글 맥락을 반영한 입력도 포함했다.

### 4.3 실행 방식

모델별 결과 파일은 다음과 같이 분리했다.

| 파일 유형 | 설명 |
| --- | --- |
| `raw_outputs-*.jsonl` | 모델별 원문 응답, 파싱 결과, latency, 자동 평가 세부 정보 |
| `auto_scores-*.json` | 규칙 기반 자동 평가 점수 |
| `judge_scores-*.jsonl` | GPT-5.5 기반 정성 평가 결과 |
| `final_summary-*.csv` | 모델별 기능 평균과 종합 결과 |
| `failure_cases-*.jsonl` | 파싱 실패, 스키마 실패, 길이 실패 등 실패 케이스 |
| `semantic_similarity_scores.csv` | Embedding Cosine과 BERTScore 세부 결과 |
| `distinct_scores.csv` | Distinct-1/Distinct-2 결과 |
| `pairwise_cosine_summary.csv` | 모델 간 출력 유사도 요약 |

### 5.4 평가 절차

평가는 아래 순서로 진행했다.

1. 각 기능별 샘플을 로드한다.
2. 기능별 프롬프트 템플릿에 입력 데이터를 넣어 모델별 prompt를 만든다.
3. 모델 응답을 생성하고 원문을 저장한다.
4. 응답에서 JSON을 추출하고 파싱한다.
5. 기능별 필수 스키마를 검사한다.
6. 한국어 출력 여부, 길이 제한, 금칙어 여부, 응답 시간을 자동 평가한다.
7. 자동 점수를 5점 만점으로 환산한다.
8. GPT-5.5 judge로 정성 평가를 수행한다.
9. `auto_score * 0.45 + judge_score * 0.55` 방식으로 최종 점수를 계산한다.
10. 저장된 raw output을 기준으로 Embedding Cosine, BERTScore-F1, Pairwise Cosine, Distinct-1/2를 추가 계산한다.
11. 기능별 평균과 모델별 종합 평균을 CSV로 저장한다.

정량 평가는 형식과 운영 안정성을 보기 위한 평가이고, 정성 평가는 실제 서비스 응답 품질을 보기 위한 평가이다. 최종 점수는 두 평가를 함께 반영하되, 사용자에게 보이는 문장 품질을 더 중요하게 보기 위해 정성 점수 비중을 55%로 두었다.

### 5.5 테스트 결과 해석 방식

`midm-base`는 품질과 감성 지표가 가장 높지만 평균 응답 시간이 길어 단일 실시간 운영 모델로는 부담이 있다. `kanana-nano-2.1b`는 빠르고 Embedding Cosine이 높지만 JSON/스키마 성공률과 다양성 지표가 낮다. `qwen-7b`는 속도에서 빠른 모델은 아니지만, 기존 Final 평균 2위, Embedding Cosine 2위, BERTScore-F1 2위, Distinct-1 1위로 품질과 의미 유사도, 다양성의 균형이 가장 좋았다.

## 8. 결론

최종 단일 모델 후보는 `qwen-7b`로 선정한다.

`qwen-7b`가 모든 항목에서 1등인 모델은 아니다. 감성 품질과 전체 Final 점수는 `midm-base`가 더 높고, 순수 속도는 `llama-3b`, `kanana-nano-2.1b`, `qwen-3b`, `gemma-3-4b-it`가 더 빠르다. 하지만 몽글마을에서 중요하게 보는 한국어 품질, 페르소나 반영, 의미 유사도, 표현 다양성을 하나의 모델로 함께 고려하면 `qwen-7b`가 가장 균형적이다. 속도는 현재 결과 기준 약점이므로, 실제 서비스 적용 전 최적화가 필요하다.
